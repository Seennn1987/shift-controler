**作成日:** 2026年8月14日

**目的:** 8-2（授業マッチング画面改善）および今後の機能追加に備え、1ファイル集中型から保守しやすい構成へ移行する

## 1. なぜ今、分割するのか

### 現状

| ファイル | 行数（目安） | 内容 |
|---|---:|---|
| `index.html`（教室長用） | 約6,200行 | HTML + CSS（約900行）+ JavaScript（約4,700行）がすべて1ファイル |
| `teacher.html`（講師用） | 約860行 | 同上。祝日データ・Firebase設定などが教室長用と重複 |

### 問題点

1. **修正のたびに6,000行超を触る** → 見落とし・不具合のリスクが高い  
2. **祝日データ（`HOLIDAYS_JP`）が2ファイルに手コピー** → 片方だけ更新するとズレる（HANDOFF.md 4-4）  
3. **8-2（スライドパネル付きマッチング）を足すとさらに膨らむ**  
4. **これから機能・改善がまだ多い** → 今整理しないと後でコストが倍になる  

### 判断

リリースまで時間に余裕があり、追加機能が多いため、**8-2に着手する前に分割する**。

---

## 2. 方針（AI選定の最適案）

### 採用案: **Vite + 素のJavaScript（React は今回使わない）**

| 選択肢 | 内容 | 評価 |
|---|---|---|
| A. 現状維持（HTML1ファイルのまま） | 追加が最速 | ❌ 8-2以降の開発がつらい |
| B. ビルドなしで `<script src>` 分割 | npm不要 | △ ファイル読み込み順・共通変数の管理が煩雑 |
| **C. Vite + 素のJS（採用）** | 開発用サーバー + 公開用ビルド | ✅ 将来のReact移行とも相性が良い |
| D. いきなり React + Vite 全面書き直し | 最も整理される | ❌ 工数が大きすぎる |

**選定理由:**

- HANDOFF.md 9章でも「Vite でビルドした静的ファイルを GitHub Pages に配信」と方針済み  
- React は**段階移行**の前提。今は JS のファイル分割だけで十分  
- Cursor で `npm run dev` → ローカル確認、`npm run build` → Web公開、が確立できる  
- 8-2以降の機能追加を **機能ごとのファイル** に書ける  

**変えないもの:**

- Firebase（認証・Firestore）  
- GitHub Pages の公開 URL（`https://seennn1987.github.io/shift-controler/`）  
- 画面の見た目・操作（ユーザーから見た挙動は維持）

## 7. リスクと対策

| リスク | 深刻度 | 対策 |
|---|---|---|
| 分割中に既存機能が動かなくなる | 高 | Phase ごとに確認チェックリストを実行 |
| 共有変数の import 漏れ | 中 | `state.js` に集約。Phase 3 は1ファイルずつ切り出し |
| GitHub Pages の URL が変わる | 低 | `base: '/shift-controler/'` を固定 |
| ビルド手順を忘れる | 中 | README + `serve.sh` を更新 |
| 講師・教室長の Firebase セッション競合 | 低 | 既知の挙動。分割では変えない |

**ロールバック:** 各 Phase 完了時に GitHub へ送信 → 問題があれば直前のコミットに戻す
